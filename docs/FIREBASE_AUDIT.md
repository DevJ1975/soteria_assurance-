## Findings by dimension

### Firestore security rules

#### 1. [CRITICAL] Tenant-subtree catch-all 'allow write' ORs over every restrictive rule, nullifying immutability, AI-field fences, delete bans, and admin-only writes

*Where:* `firestore.rules`:109 — *area:* firestore-rules/structure

firestore.rules:109-118 grants `allow write` (create+update+delete) on /tenants/{tenantId}/{document=**} to roles super_admin/tenant_admin/lead_auditor/auditor. Firestore security rules grant access if ANY overlapping match block allows it; the comment at firestore.rules:107 ('the most specific match wins') is wrong — there is no specificity precedence. Consequences, each contradicting an explicit rule below: (1) findings: delete ban (line 172), post-report immutability (162), AI-field fence (164) and lead_auditor-only nonconformityStatement (165-170) are all bypassed — any 'auditor' can delete findings, edit them after report_issued, and write aiDraftStatement, directly violating docs/DESIGN_DOC.md:1538-1544 ('Findings become read-only... Firestore security rules enforce immutability at the database level'). (2) evidence: delete ban (193), immutability (189) and aiAnalysis/aiHazardsDetected fence (191) bypassed. (3) aiLogs: `allow write: if false` (216) bypassed so auditor+ can forge or delete the AI audit trail, and the SA/TA/LA-only read (214-215) is bypassed because the catch-all read (111) only requires hasValidRole, letting auditee/viewer read aiLogs. (4) users: admin-only write (137-138) bypassed — auditors can create/update/delete user documents (packages/core/src/constants/rbac.ts: manage_users is super_admin/tenant_admin only). (5) Because rules_version='2' (line 1) makes {document=**} match zero or more segments, the catch-all also matches /tenants/{tenantId} itself, bypassing the admin-only update and `delete: if false` on the tenant document (126-128) — an auditor can rewrite tenant settings or delete the tenant doc. (6) correctiveActions delete ban (205) bypassed. Tenant isolation itself is NOT affected: belongsToTenant(tenantId) is required in the catch-all, and claims are only minted server-side (functions/src/auth setTenantClaims, which pins tenant_admin callers to their own tenantId).

**Fix:** Remove `allow write` from the catch-all block (keep the tenant-scoped read, or enumerate reads per collection too), then add explicit match blocks for the remaining client-written collections (clients, audits, meetings, witnessStatements, clauses, reports, templates) with the intended role gates, relying on the existing default-deny (firestore.rules:240-242) for everything else. Redeploy with `firebase deploy --only firestore:rules` and add rules-unit-tests (@firebase/rules-unit-testing) asserting auditor cannot delete findings, write aiLogs, or edit the tenant doc.

#### 3. [MEDIUM] AI-field fence only applies on update, not create — and the shipped client flow actually writes aiDraftStatement from the client

*Where:* `firestore.rules`:156 — *area:* firestore-rules/ai-fields

The AI-field fence in firestore.rules applies only to updates, not creates, contradicting the file's own guarantee. The header (firestore.rules:26-27) asserts AI-only fields "can never be set by a client," but the findings create rule (156-158) and evidence create rule (183-185) place no constraint on request.resource.data, so any tenant client with an auditor+ role can create documents with aiDraftStatement/aiAnalysis (findings) or aiAnalysis/aiHazardsDetected (evidence) pre-populated; only updates are fenced (164, 191). The shipped mobile flow actively relies on this create-path gap for findings: draftNCR returns the AI draft to the client (apps/mobile/services/aiService.ts:51-58), the form submits it (FindingForm.tsx:183), createFinding stores it locally (auditRepository.ts:158), findingToDoc includes it in the Firestore payload (mappers.ts:104), and the sync manager's first push is a plain non-merge setDoc — a rules-level CREATE — carrying the client-supplied aiDraftStatement (syncManager.ts:117; packages/firebase/src/firestore.ts:296-301). Two precisions vs. the original claim: (1) for evidence, the create-rule gap exists but the shipped client never writes aiAnalysis/aiHazardsDetected (evidenceToDoc, mappers.ts:111-132, omits them) — the live contradiction is findings/aiDraftStatement only; (2) the update fence is diff-based (notUpdating uses affectedKeys), so later full-doc re-pushes with an unchanged aiDraftStatement also pass, which is why the flow works end-to-end today. Impact: not privilege escalation, but the documented server-only provenance of AI fields is false — a client can fabricate or tamper with "AI-authored" content at creation time, undermining the AI-provenance/audit-defensibility guarantee the rules claim. Fix: pick one model — (a) accept aiDraftStatement as client-persisted provenance and fix the misleading header/comments (and ideally fence only aiAnalysis/aiHazardsDetected on create), or (b) enforce server-only by adding a keys().hasAny() guard to both create rules and having Functions write AI fields via the admin SDK — noting (b) breaks the current mobile sync push unless aiDraftStatement is removed from findingToDoc/createFinding first.

**Fix:** Pick one model and align both sides. Either (a) treat aiDraftStatement as client-persisted provenance: delete the misleading fence/comments, or (b) keep it server-only: add `&& !request.resource.data.keys().hasAny(['aiDraftStatement','aiAnalysis'])` to the findings/evidence create rules and have the draftNCR/analyzeEvidence functions write the fields with the admin SDK; then remove aiDraftStatement from the mobile create/push path.

*Where:* `apps/mobile/services/syncManager.ts`:117 — *area:* firestore-rules/sync-interaction

Mobile sync pushes whole documents with no merge: setDocById (packages/firebase/src/firestore.ts:296-301) fully overwrites, and syncManager uses it for findings (apps/mobile/services/syncManager.ts:117) and evidence (:144). Fix as proposed: push deltas (patchDoc/{merge:true} already exists at firestore.ts:303-312) or round-trip all server-authored fields, and treat permission-denied as a terminal 'rejected' sync state. Severity medium is appropriate (data-loss mechanism is real but currently latent; becomes active/user-visible as soon as fences or server-authored fields land).

**Fix:** Push deltas instead of whole documents: use updateDoc/setDoc({merge:true}) with only locally-changed fields, or at minimum have the mappers round-trip all server-authored fields pulled at hydration. #### 5. [MEDIUM] RBAC matrix rows close_ncs and create_audits are not enforced, and auditees can self-review/close their own corrective actions

*Where:* `firestore.rules`:160 — *area:* firestore-rules/rbac

RBAC matrix rows close_ncs and create_audits are not enforced by firestore.rules, and auditees can self-review/close their own corrective actions. (1) close_ncs is SA/TA/LA-only (rbac.ts:49,91-98), but the findings update rule (firestore.rules:160-170) lets role 'auditor' set status:'closed', closedAt and closedByAuditorId — only aiDraftStatement/aiAnalysis and nonconformityStatement are fenced. Correction to the mobile evidence: setFindingStatus (apps/mobile/services/auditRepository.ts:177-189) writes only `status` (the sync mapper, mappers.ts:100, pushes status but has no closedAt/closedByAuditorId fields) and currently has no UI call site — it is an exported client-side closure pathway rather than a live flow; the rules gap stands regardless because rules must hold against arbitrary client writes. (2) create_audits is SA/TA/LA-only (rbac.ts:45), but there is no audits-specific match block — audit docs fall solely under the catch-all (firestore.rules:109-118) whose write set includes 'auditor' (:116-117); audit creation is purely client-SDK (NewAuditWizard.tsx:130; mobile syncManager.ts:72) and no deployed function creates audits (functions/src/index.ts:11-25), so rules are the only enforcement point. (3) The correctiveActions rule (firestore.rules:201-206) grants auditee create/update with no field fencing, so an auditee (the audited party) can set status to 'accepted'/'closed' (CAStatus, finding.ts:18-24) and write reviewedByAuditorId, reviewNotes, effectivenessResult, reviewedDate/closedDate and even the AI-authored aiRootCauseSuggestion (correctiveAction.ts:42,52-53,60-64) — CA acceptance/closure is a close_ncs (SA/TA/LA) operation; auditee holds only manage_corrective_actions (submission). Related note (accurate, safe direction): every tenant rule requires belongsToTenant (:109-118,124-128), so a super_admin client only reaches its claimed tenant despite manage_tenants being platform-wide in rbac.ts:43; cross-tenant admin must go through the admin SDK.

**Fix:** In the findings update rule, fence closure fields: allow status transitions to 'closed' (and closedAt/closedByAuditorId writes) only for hasRole(['super_admin','tenant_admin','lead_auditor']). Add an audits block restricting create to SA/TA/LA (see the audit-status finding). In correctiveActions, split auditee updates to a whitelist via onlyUpdating() (e.g. rootCause*, immediate/corrective/preventiveAction, closureEvidenceIds, closureNotes, submittedDate, status transitions limited to 'in_progress'/'submitted', history/updatedAt) and reserve reviewer/closure fields for SA/TA/LA.

#### 6. [MEDIUM] isAuditReported get() is billed on every findings/evidence write attempt, and mobile sync will re-attempt permanently denied writes on every pass

*Where:* `firestore.rules`:84 — *area:* firestore-rules/cost-loops

Every client findings/evidence create and update evaluates isAuditReported (firestore.rules:84-87, invoked at 158, 162, 185, 189): exists()+get() on the same parent-audit document, billed as one document read per write request, charged whether the write is allowed or denied. The mobile sync manager re-attempts every non-'synced' row on each pass — 'failed' rows match UNSYNCED (apps/mobile/services/syncManager.ts:45; markRowFailed at 166-172) — and the catch blocks (120-123, 147-150) discard the error, so permission-denied is never treated as terminal (no retry cap, no backoff). runSync is triggered via scheduleSync (syncManager.ts:235-239) after every UI mutation (auditRepository.ts:87, 172, 188, 207; evidenceService.ts:160) and by the manual sync button (settings/index.tsx:63); a connectivity-driven trigger is documented (app/_layout.tsx:10, syncManager.ts:7-8) but its SyncProvider file is missing from the repo (app/_layout.tsx:26 imports ../lib/SyncProvider, which does not exist — separate breakage), so today retries fire on mutations and manual taps. Once the critical catch-all bypass (firestore.rules:109-118 ORs an unconditional auditor-role write over the specific immutability rules) is fixed, the designed lifecycle — audit reaching 'report_issued' (packages/core/src/types/audit.ts:17) while a device still holds pending findings/evidence rows — produces writes denied by !isAuditReported on every retry, forever: each retry burns one rules-get() read per row and pins the sync indicator on 'failed' (syncManager.ts:222-224; auditStore.ts:87-91), with no client-side pre-check of the locally known parent audit status (pushFindings/pushEvidence, syncManager.ts:107-153) before pushing. Fix: skip pushing findings/evidence whose parent audit is locally 'report_issued', and classify Firestore permission-denied as terminal (stop requeueing) rather than generic 'failed'.

**Fix:** Before pushing findings/evidence, have the sync manager skip rows whose parent audit is locally known to be report_issued, and classify Firestore 'permission-denied' as terminal (do not requeue). Optionally denormalize a `reportIssued: true` flag onto the audit at issuance so the rules can keep using a single get() while clients can cheaply pre-filter.

### Storage security rules

#### 9. [HIGH] Tenant-wide catch-all rule silently overrides every stricter per-path rule (including server-only reports)

*Where:* `storage.rules`:111 — *area:* storage-rules

Firebase Storage rules grant access if ANY matching rule allows, and under rules_version '2' (storage.rules:1) the catch-all `match /tenants/{tenantId}/{allPaths=**}` (storage.rules:111-117) matches every object under a tenant, allowing create/update for super_admin/tenant_admin/lead_auditor/auditor with only a <500MB size check (storage.rules:49-51). This nullifies: (1) `tenants/{t}/reports/{f}` `allow write: if false` (storage.rules:87, 'Server-only') — any auditor can create or OVERWRITE generated audit-report PDFs, defeating the server-only-report intent (storage.rules:83-84) and the immutability posture in the header (storage.rules:14-19) on an ISO 45001 compliance product; (2) evidence `isValidImage()` (image/* + <25MB, storage.rules:59-61, 42-45) — staff can put any content type up to 500MB at evidence paths; (3) signatures `isValidImage()` (storage.rules:77-79) for staff roles — only `auditee`, absent from the catch-all role list (storage.rules:114), remains bound; (4) branding admin-only writes (storage.rules:103-105) — lead_auditor/auditor can overwrite tenant logos with arbitrary <500MB content. One correction to the original detail: deletes are not denied "everywhere" — the branding block itself intentionally allows delete for super_admin/tenant_admin (storage.rules:103,105). The accurate statement is that the catch-all adds no delete permission (its `allow delete: if false` at storage.rules:116 grants nothing), so evidence/recordings/signatures/reports deletes remain denied as intended. Fix as proposed: remove the catch-all or reduce it to `allow read` only (default deny at storage.rules:120-122 plus the explicit per-path blocks already cover intended access), then redeploy via scripts/deploy.sh --only rules (scripts/deploy.sh:86-89).

**Fix:** Remove the catch-all block (rely on the explicit per-path rules plus the default deny at storage.rules:120-122), or reduce it to `allow read` only. If a write catch-all is truly wanted, scope it to paths that don't overlap the specific matches. Then redeploy rules (scripts/deploy.sh --only rules).

#### 11. [MEDIUM] Evidence 'immutability' blocks delete but permits in-place overwrite (tamper-by-update)

*Where:* `storage.rules`:59 — *area:* storage-rules

The rules' stated goal (storage.rules:14-19) is that evidence must not be client-destroyable, and delete is denied outright (storage.rules:62, 71, 80). But `allow update` (storage.rules:59, 68, 77) lets any same-tenant member holding a staff role overwrite an existing evidence/recording/signature object with different bytes at any time — destroying the original as effectively as deletion (e.g. replacing an incriminating photo after the report is issued). No Cloud Function watches storage objects and no content hash is stored, so tampering is undetectable app-side. The legitimate flow is effectively write-once: filenames are Date.now()-prefixed and uploaded once (apps/mobile/services/evidenceService.ts:85, packages/firebase/src/storage.ts:72-83). One caveat to 'update is pure attack surface': the retry path (evidenceService.ts:132-161, 167-178) re-uploads to the same fileName after a client-observed failure, so if the earlier attempt actually committed server-side, the retry is technically an update — a blunt `allow update: if false` would wedge such rows in 'failed'. Fix: split verbs (`allow create` with existing conditions, `allow update: if false`) on the evidence, recordings, signatures — and also the correctiveActions (storage.rules:92-98) and tenant catch-all (storage.rules:111-117) matches which share the pattern — and have the client treat a permission-denied retry against an existing object as success (or verify existence before retrying). Keep update only where overwrite is a real use case (branding, storage.rules:101-106).

**Fix:** Split the verbs: `allow create: if ...` with the existing conditions and `allow update: if false` on the evidence, recordings, and signatures matches (keep update only where overwrite is a real use case, e.g. branding).

Linux/CI (bash 5) is unaffected, so this bites exactly the local-developer flow the script is documented for.

**Fix:** Use the portable guard `${FIREBASE_FLAGS[@]+"${FIREBASE_FLAGS[@]}"}` at the three call sites, or build a plain string, or require bash >= 4.4 explicitly.

#### 42. [INFO] Node pins are mutually consistent at 20, but local toolchains on Node 22 violate functions' exact engines pin (warning + emulator/prod drift)

*Where:* `functions/package.json`:7 — *area:* node-version

The pins agree everywhere it matters: .nvmrc:1 = 20, CI node-version 20 (deploy-hosting.yml:61), functions runtime nodejs20 (firebase.json:13), functions engines "node": "20" (functions/package.json:6-8). However the root engines is the looser ">=20" (package.json:7-9), and this environment demonstrates the gap: it runs Node v22.22.2, which satisfies the root constraint but violates functions' exact "20" — pnpm emits engine warnings (non-fatal, engine-strict off), and `firebase emulators:start --only functions` executes function code on 22 while production runs on 20, a subtle behavioral-drift risk. This is exactly the 'local v22 warning' scenario; .nvmrc protects only nvm users.

**Fix:** Have developers adopt the .nvmrc (nvm use / fnm / volta pin), or set engine-strict=true in .npmrc to turn the mismatch into a hard error, or relax functions engines to "^20" only if 22-vs-20 drift is accepted for the emulator.
